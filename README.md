# SteamTools Python 改造：思路与原则


## 一、目标

原版 SteamTools / WattToolkit 是 C# + Avalonia 的桌面工具，核心能力之一：通过本地代理 + 规则把「被墙/缓慢的域名」转发到可用中转（或固定 IP）并做 SNI/Host 伪装，同时尽量不影响其它网站（未命中规则直接透传）。
steamtools-py 是其 Linux 无 UI 版本：只保留代理核心 + CLI + 引流（hosts / 系统代理 / PAC），供服务器（如校园网内一台常开机器）对外提供加速代理。
本文把原桌面工具里“让特定站点更快、更稳、更容易访问”的能力，迁移到一个**无界面、可长时间常驻、可被远程客户端使用**的服务形态。



改造成功的标准不是“功能列表对齐”，而是：

- 目标站点在真实客户端上**可访问且体验稳定**；
- 对**不相关的流量无感**（不干扰、不改变安全预期）；
- 出问题时**能自动降级、能定位、能恢复**。

## 二、总体思路（六条主线）

1. **先分流，再处理**
   只有明确属于“需要加速”的目标才接管；其余一律尽量原样通过。
   分流越准，改造的风险面越小，用户的“副作用”感知越低。

2. **终结—改写—再发出**
   要能改写请求、控制超时、观察结果，就必须在本地以“可信的中间人”身份接住连接，再以“被目标认可的”身份向出口发起新连接。
   这是所有“加速 + 伪装”能力的共同前提。

3. **出口可优选，也可替换**
   为同一目标准备多个可用出口，按实际延迟择快、择优结果短期记忆、连续失败自动隔离。
   “主出口 + 备用出口”要成为默认思维，而不是异常处理。

4. **伪装要两头兼顾**
   对出口：以对方期望的域名与请求特征出现，避免被拒或被降级。
   对客户端：不要改变它的安全预期——能沿用既有信任关系就不要让用户重新配置。

5. **引流方式按环境选择**
   本地名称映射、显式代理、自动配置脚本三种形态各有适用场景（本机全量、跨机显式配置、浏览器级选择）。
   形态可以不同，但**背后的转发与加速逻辑应当统一**，避免行为漂移。

6. **可控性优先于峰值性能**
   配置集中可改、行为随时可见、异常能归类、退出能清净（不留下影响系统的残留）。
   长期常驻的服务，可运维性的价值高于极限吞吐。

## 三、关键设计取舍

| 取舍 | 一侧 | 另一侧 | 建议 |
| --- | --- | --- | --- |
| 接管范围 | 全量接管，能力最强 | 只接管命中目标，最不打扰 | 默认只接管命中目标，保留“全量”作为可选 |
| 上游连接 | 复用连接，性能好 | 每次新建连接，互不影响 | 复用 + **单请求级故障隔离**，别让一个慢请求拖垮整批 |
| 探测与稳定 | 频繁探测，选路最准 | 少探测，开销小、抖动少 | 冷启动择优 + 短期记忆 + 过期重探 |
| 证书信任 | 自建信任根，完全自主 | 沿用既有信任关系，用户零改配置 | 优先沿用；自建时把“安装信任”做成一步操作并明确提示 |
| 自研与依赖 | 用成熟组件，省事 | 自研关键路径，能力可控 | 只有当现成方案**无法满足“停滞可控 / 单点故障不扩散”**时才自研，并接受其维护成本 |
| 失败处理 | 立即报错，行为清晰 | 自动回退，用户无感 | 可重试的失败先回退（如回退直连、回退备用出口），并把过程写进日志 |

## 四、必须守住的原则

1. **透明优先**：未命中的流量不被改写、不被解密、不产生证书告警。
2. **等价迁移优先于优化**：先做到与原实现行为一致，再谈性能与重构。
3. **渐进替换，随时可退**：新路径与旧路径可共存，能一键切回。
4. **失败必须可解释**：错误分类要能回答“谁的问题”——客户端、网络、出口、还是服务本身。
5. **故障半径最小化**：单个目标、单个请求、单个出口出问题，不能演变成整体不可用。
6. **区分“慢”和“卡”**：对长时间无进展的连接要主动了结，而不是无限等待；且只了结相关部分。
7. **安全边界前置**：一旦服务暴露到公网，认证就不是可选项；默认配置也不应假设“内网安全”。
8. **验证驱动**：动手前先定义验收现象（见第五节），否则容易“功能都在、体验不行”。

## 五、验收思路（现象级，不看实现）

按顺序逐层通过，任一层不过就不进入下一层：

1. **单点可通**：目标站点返回正常内容。
2. **多点可通**：命中与未命中的站点分别成立（前者加速、后者透明）。
3. **真实页面可用**：一个页面（含大量并发子请求）能完整加载——这是最容易被忽略、也最容易暴露问题的一层。
4. **长时间稳定**：连续运行数天，无性能持续劣化、无资源泄漏、无进程意外退出。
5. **故障可降级**：注入异常（出口卡死、出口断开、名称解析异常、客户端中途取消）后，服务仍可用且只影响相关请求。
6. **日志可判读**：只看日志就能判断失败发生在哪一层、是否影响他人、是否属正常现象。
7. **可恢复**：服务重启后行为一致；异常退出不残留对系统的改动（引流、系统设置等）。

## 六、主要风险与对策

| 风险 | 表现 | 对策思路 |
| --- | --- | --- |
| 误伤透明流量 | 普通网站报证书错、被改写 | 严格按命中规则解密；未命中直接通过 |
| 信任链问题 | 客户端大面积“握手失败” | 复用既有信任；自建根时提供明确安装步骤与检测提示 |
| 单点依赖 | 一个出口/中转失效导致某站全挂 | 备用出口 + 自动回退直连 |
| 故障扩散 | 一个慢请求拖慢同批其它请求 | 请求级隔离与超时，不共用“命运” |
| 开放代理滥用 | 端口暴露后被他人使用 | 强制认证、按需收敛监听范围 |
| 配置漂移 | 不同环境行为不一致、难以复现 | 配置集中、启动即记录生效值 |
| 残留状态 | 退出后系统设置/引流未还原 | 退出与启动都做清理与兜底，并提供独立清理入口 |

---

## 七、演进路线（建议顺序）

1. **打通**：先让一条最小路径在真实客户端上可用（验证方向正确）。
2. **稳健**：补齐超时、回退、故障隔离，让它在坏网络下也不崩。
3. **兼容**：覆盖真实客户端的完整行为（并发、长连接、异常中断），不被“单次请求能通”迷惑。
4. **可运维**：日志分层可读、配置可调、状态可查、清理可靠。
5. **多形态**：在统一内核之上提供不同引流形态与部署方式。

---

## 八、给接手者的一句话

> 先把“透明、可退、可解释”做扎实，再追求“更快、更强”；
> 每一次改动都要能回答：**对未命中的流量做了什么？失败了会怎样？怎么证明它没变坏？**
